# ecagent
Agentic AI assistant for discovering and planning extracurricular activities

## Repo Structure


## Setup

```bash
pip install -r requirements.txt
export ANTHROPIC_API_KEY=...        # all modules use claude-sonnet-4-6 (MODEL in utils.py)
                                    # Windows PowerShell: $env:ANTHROPIC_API_KEY="..."
python -m scraper.scrape            # build data/campus.db (real use; the eval uses data/fixtures/, see Tests)
```

Run everything from the repo root (imports are `agent.*`, `scraper.*`, `utils`).

### Tests

```bash
python -m eval.fixtures.build_fixtures                          # eval DBs (the offline eval tests build them too)
python -m unittest discover -s unit_tests -t . -p "test_*.py"  # offline, free
ECAGENT_LIVE_TESTS=1 python -m unittest unit_tests.test_live -v  # real API calls (costs a little), needs ANTHROPIC_API_KEY
```

### Eval

```bash
python -m eval.eval "what changed"   # full eval: 3 trials per agent per eval_instance (324 trials) -> eval/results/results.json
python -m eval.pipeline_check       # 1 trial per agent per eval_instance (108 trials, ~$6), docs/pipeline-check.md
python -m eval.manual_grading       # manual labels + quality for the last batch in eval/results/results.json
```

The full eval hasn't been run yet; the README TODOs from the pipeline check come first. Each run is a new batch in `eval/results/results.json`, timestamped by its start time (`batch_id`) with its description; earlier runs are never replaced. Each batch stores its step 7 report (`report`, `docs/agent.md` Experimental Setup), undecided (`None`) until manual grading is done and recomputed after every `manual_grading` session.

### Google Calendar + Gmail (real use)

Secrets stay **outside the repo**, in the folder that contains it (`../client_secret.json`,
`../google-token.json`; override with `ECAGENT_SECRETS_DIR`).

1. [Google Cloud console](https://console.cloud.google.com), signed in as the test account: create a project.
2. **APIs & Services → Library**: enable **Google Calendar API** and **Gmail API**.
3. **Google Auth Platform** (OAuth consent screen): Branding (app name, support email); Audience: External,
   add the test account under **Test users**.
4. **Clients → Create client → Desktop app**, download the JSON, save it as `../client_secret.json`.
5. Log in once (opens the browser), then run the live test:

```bash
python -m scripts.google_login      # rerun when it expires: every 7 days while the app is in Testing mode
python -m scripts.live_test         # calendar: add/read back/remove a test event; gmail: read + extract
python -m scripts.live_test --agent --interests photography   # then chat with the whole agent
```

The agent reads the primary calendar (busy time) and adds approved activities to a separate **ECAgent**
calendar. Gmail is read only: announcement emails become activities to recommend, the student's own
commitments (exams, interviews) become busy time. Scopes: `calendar`, `gmail.readonly`.

## Usage

```python
from agent.agent import ECAgent

agent = ECAgent(memory_path="memory.json")          # memory saved after each turn
reply, selection = agent.run("Can you find me an activity that works with my schedule?")

# real accounts (after the Google setup above)
from agent.calendars import GoogleCalendar
from agent.gmail import EmailSource, GmailInbox
agent = ECAgent(calendar=GoogleCalendar(), inbox=EmailSource(GmailInbox()))
```

`run` returns the reply and the activities shown or added this turn. Plans are only added to the calendar
after the student approves them in the next message: a separate yes/no check (`check_approval`) runs first,
and `register` / `calendar` are only offered to the router (and only executed) when it says yes. Every add
and remove is verified by reading the calendar back; a failed add is retried once, without duplicates.

Eval uses `SimulatedCalendar(events=..., fail_on=...)` and `SimulatedRegistration(fail_on=...)`
(e.g. `fail_on={1}` for task 9's tool error), `inbox=None` and `use_web=False`.

## TODO
- **Re-check event details** (`agent/scheduler.py`) right before adding, since approval can come days after the proposal.
- **Outlook messages as an event source**: a second inbox with the same `scan()` interface as `agent/gmail.py` (Microsoft Graph `/me/messages`, `Mail.Read`).
- **Simulated inboxes** for the eval profiles, if email should be part of the benchmark.
- **Club meeting times** (`agent/retriever.py`): fetches meeting times from club websites (web_fetch) so clubs become schedulable events.
- **Semantic search** (`agent/retriever.py`): replaces or supplements the keyword search of the DB.
- **Retrieve before replying** (`agent/agent.py`, `run`/`route`): when a message asks for activities and nothing has been retrieved this turn, run the retriever first in code instead of trusting the router's first choice. The pipeline check found the router picks `user` for requests that name no interest ("Can you find me an activity?"), so `full_agent` and `no_compact` picked nothing in 14/36 instances each (`docs/pipeline-check.md`, finding 1). Also covers the approval turn that lost the earlier results (finding 3).
- **No false "no data" claims** (`agent/agent.py`, `step_user`): only tell the student nothing was found if the retriever actually ran and came back empty (pipeline check: 25 of 31 no-pick replies falsely said the activity list was empty).
- **Response check without activities** (`agent/agent.py`, `verify_response`): also run it when no activities are shown, since claims about the data ("my list is empty", "I fabricated that") need checking too.
- **Register only when asked** (`agent/agent.py`, `available`): offer `register` to the router only when the request asks for registration (pipeline check: unrequested registration in 26 trials). Also what `Verifier.check_request` is for.
- **Full profiles x tasks cross product** (`eval/benchmark-tasks.json`, `eval/profiles/generate_profiles.py`, `eval/fixtures/`): our original design (writeups, `docs/agent.md` step 4) runs every profile on every task (5 x 10 = 50 eval_instances). The eval currently runs 36, because 4 tasks only list the profiles that have the material they need: `multi-restriction` and `resolve-conflicting` (P2, P3: restrictions / conflicting ranked preferences), `adapt-schedule` (P4: the only runtime update that clashes with a planned activity), `long-context` (P5: the only long history). Matching the original design needs that material for the 14 missing pairs (runtime updates for P1-P3 and P5, conflicting preferences for P1, P4, P5, long histories for P1-P4, plus fixture answer keys), without changing what each task tests.
- **Verifier** (`agent/verifier.py`): replace `ECAgent.verify_response` with `Verifier.verify_response` (grounded, likes/dislikes + constraints the data can't show, schedule constraints, original request; any failure --> replan). Not called yet because it must be motivated by eval first (e.g. `interest` / `no_avoid` / `hard_constraints` checks failing on the fixture answer keys).
- **Web search in the eval** (off for now, `use_web=False`): web results are outside the fixture answer key, so they can't be graded objectively yet. Suggestion: in the eval, swap the server-side `web_search`/`web_fetch` for a client-side tool with the same schema that returns "web results" written into the task's fixture (labeled in its answer key like the DB rows). Same tools for every agent, deterministic, objective. Real use keeps the real web tools.
- **Other embedding models** (`docs/scripts/interest_test.py`): compare against `all-MiniLM-L6-v2` (e.g. `all-mpnet-base-v2`) and re-pick the cutoff. Only relevant if relevance is ever scored on real data (the eval uses fixture answer keys, `docs/design-decisions.md`, Why relevance is not scored on real data); events are the weak spot.
